# Playwright 自动化测试编写与修复指南

当用户要求你编写、修改或修复 Playwright 测试用例时，必须严格遵守以下规范：

## 1. 代码生成规范
- **使用 PO (Page Object) 模式**：绝对禁止在 `.spec.ts` 测试文件中直接写元素定位器。必须将页面操作封装到 `pages/` 目录下的类中，测试步骤写在 `tests/` 目录下。
- **定位器优先级**：强制使用 `getByRole` > `getByTestId` > `getByText` > `getByLabel`。严禁使用脆弱的 CSS/XPath 选择器。
- **断言要求**：所有的断言必须使用 `expect`，且在 UI 操作后必须有显式的断言。

## 2. 交互验证规范 (防止假通过)
- **不要只信任前端 UI**：在点击“提交”或“保存”按钮后，不能只断言弹出了成功提示框 (Toast)。
- **必须验证业务状态**：
  - 检查核心业务网络请求 (Network Request) 的 HTTP 状态码是否为 200。
  - 验证页面是否成功跳转到了预期的 URL。
  - 验证核心业务元素是否发生了预期的变化（如列表多了一条数据）。

## 3. 修复与调试流程
- **先运行再交付**：每次生成或修改完测试代码后，你必须先在本地运行该测试。
- **自动修复**：如果测试报错，你需要分析报错日志。如果是定位器问题，自行修正定位器；如果是环境问题，提示用户。
- **保留截图**：在关键的业务状态转换节点，添加 `await page.screenshot({ path: 'screenshots/key-step.png' });` 作为留证。
